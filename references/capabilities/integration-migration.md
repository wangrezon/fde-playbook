# 集成与迁移三动作

## R — 原文 (Reading)

> 第一个动作，把连线变成清单。……第二个动作，先打通一条哪怕最细的真实链路。……第三个动作，数据迁移要先彩排，先定好数据对账的标准。
>
> — 曹犟，第 9 讲

## I — 方法论骨架 (Interpretation)

集成是新客户上线的「沉默杀手」——架构图看着简单，真正动起来处处是承重墙。三个动作把风险前置：

1. **把连线变成清单**：架构图上每根外部系统连线都落地成明细——接哪个接口、鉴权方式、数据字典谁说了算、限流多少、有无测试环境、联调窗口找谁约。
2. **先打通一条最细的真实链路**：开工第一周就用客户真实环境打通一条端到端数据链路（哪怕一天同步一条记录），把鉴权、网络、权限这些承重墙提前「撞」出来。
3. **数据迁移先彩排、先定对账标准**：小批量试跑，跑之前就跟客户约好「对上账」——对哪几个指标、允许多大误差、谁签字确认。否则账永远对不完。

另需给集成单列预算，并预留资源处理长尾场景。

## A1 — 应用示例 (Application Example)

### 示例 1：新客户接入三个外部系统（合成演练，规则可复算）
- **类型与来源**: 原书未提供完整案例，以下为合成演练
- **问题/输入**: 新客户要接 3 个外部系统 + 迁移 2 年历史数据
- **方法论的使用**: 连线成清单逐项确认→第一周用客户真实环境打通一条最细数据链路→迁移前小批量试跑并约好对账三要素（指标/误差/签字人）
- **结论**: 承重墙（鉴权/网络/权限）在开工第一周就暴露，而非上线前夜
- **结果**: 合成演练输出，非作者经历

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新客户上线，要对接多个外部系统
2. 历史数据要迁移，担心「账对不上」
3. 集成联调反复延期，想找出卡点
4. 项目到了集成阶段，不知道从哪下手

### 语言信号 (用户的话里出现这些就应激活)

- 「怎么对接外部系统」「集成清单怎么列」「先打通哪条链路」
- 「数据迁移怎么对账」「对账标准怎么定」「联调老延期怎么办」
- 英文: "integration checklist", "data migration reconciliation", "system integration", "end-to-end link"

### 与相邻 skill 的区分

- 与 `code-placement` 的区别：本卡是「接线、迁移、对账」，code-placement 是「需求/代码写在哪」。
- 与 `go-live` 的区别：本卡是「集成迁移」环节，go-live 是「上线六项检查 + 治理」的最后一关。

## E — 可执行步骤 (Execution)

**必需输入**: 外部系统连线图 + 待迁移历史数据 + 客户对账口径。缺「对账口径」时先跟客户约「对哪几个指标、允许多大误差、谁签字」，不自行拍板。

**交付物与完成标准**: 集成明细清单 + 一条打通的真实链路 + 数据对账标准（三要素）。

1. **连线变清单**
   - 完成标准: 每根连线都有接口/鉴权/数据字典/限流/联调窗口明细，逐项确认。
2. **打通最细真实链路**
   - 完成标准: 开工第一周用真实环境跑通一条端到端链路，鉴权/网络/权限问题已暴露并记录。
3. **迁移彩排 + 定对账标准**
   - 完成标准: 小批量试跑完成；对账三要素（指标/误差/签字人）已与客户书面确认。
4. **留长尾预算**
   - 完成标准: 集成有单列预算，长尾场景有专人/专项资源。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还在填 gap、写生产代码——那是 code-placement 的职责
- 已经集成完、要过上线检查——那是 go-live 的职责
- 没有外部系统/数据迁移的纯功能开发——本卡不适用

### 作者在书中警告的失败模式

- 「账永远对不完」：迁移前没定对账标准，事后补对账，历史数据永远迁不利索。

### 作者的盲点 / 时代局限

- 作者仅给「专门预留资源处理长尾场景」，未给长尾占比或识别判据的量化方法，需自行估算长尾规模。

### 容易混淆的邻近方法论

- 「先通最细链路」与「先做全量设计」相反——本卡要求先撞承重墙，不要等到所有设计图完美才开始。
