# 上生产（六项检查 + 治理 + 留痕 + HITL）

## R — 原文 (Reading)

> 第一项，评估过线。第二项，真实规模下的性能与成本。第三项，安全与权限。第四项，全链路留痕与决策可追溯。第五项，应急与回滚预案。第六项，运营与交接流程。
>
> — 曹犟，第 12 讲

## I — 方法论骨架 (Interpretation)

「个人好用」和「企业可用」是两个问题。让 CIO 放心的上生产检查六项：评估过线、真实规模下的性能与成本、安全与权限、全链路留痕与决策可追溯、应急与回滚预案、运营与交接流程。六项通过后仍要灰度上线（小流量低风险跑一两周再放量）。

配套治理三件事：

- **五类治理风险双列负责人**：模型风险（首席风险官/数据科学）、数据风险（安全负责人）、工作流风险（运营负责人）、供应商风险（按管关键供应商方式管）、治理风险（合规团队）；风险表写两列名字——客户列（决策人）+ FDE 列（对口人）。
- **全链路留痕四类**：决策依据、数据来源、操作记录、反向回滚——从输入、上下文、prompt 到推理、工具调用、输出全程留痕。
- **HITL 人工检查点**：按风险分三级——自动执行、执行后通知、执行前确认。花钱动作（调价/扩预算）必须执行前确认；只读分析放开；放权由数据（采纳率+兑现率）而非意愿决定。

## A1 — 应用示例 (Application Example)

### 示例 1：BBVA 3300 人试用扩到 12 万员工（转述）
- **类型与来源**: 原书转述，第 19 讲
- **问题/输入**: 西班牙 BBVA 与 OpenAI 合作，没有一步到位全员铺开
- **方法论的使用**: 先 3300 名员工试用，看到持续使用 + 自报例行工作时间下降后逐步扩范围
- **结论**: 强监管行业每轮扩展建立在上一轮真实使用数据上，而非一次性铺开
- **结果**: 最终覆盖 12 万名员工

### 示例 2：花钱动作的 HITL（合成演练，规则可复算）
- **类型与来源**: 原书未提供完整案例，以下为合成演练
- **问题/输入**: 一个 Agent 要上线，含「扩预算」这类花钱动作
- **方法论的使用**: 六项逐查；花钱动作归「执行前确认」、只读分析放开；风险表写客户决策人 + FDE 对口人两列
- **结论**: 通过六项后灰度上线小流量跑一两周再放量
- **结果**: 合成演练输出，非作者经历

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. Agent/demo 已通过，要正式上生产
2. 客户 CIO/合规部门要求「上生产前的检查清单」
3. 要设计治理方案（谁负责什么风险、怎么留痕、哪里设人工检查点）
4. 上线后出了事故，要复盘「当初漏查了什么」

### 语言信号 (用户的话里出现这些就应激活)

- 「上生产要检查什么」「六项检查清单」「CIO 要的治理方案」
- 「怎么设人工检查点」「全链路留痕怎么留」「灰度上线怎么放量」
- 英文: "go-live checklist", "production readiness", "HITL", "audit trail", "governance"

### 与相邻 skill 的区分

- 与 `eval-driven` 的区别：eval-driven 产出的评估集是本卡「第一项评估过线」的来源。
- 与 `safety-guardrails` 的区别：本卡的「第三项安全与权限」是 safety-guardrails 五件套的引用。
- 与 `demo-driven` 的区别：demo-driven 到 demo 为止，本卡是「硬化 + 上生产」的后半程。

## E — 可执行步骤 (Execution)

**必需输入**: 已通过 demo/评估的系统 + 真实规模数据 + 风险动作清单。缺「真实规模验证」时先做压测，不拿 demo 数据当生产依据。

**交付物与完成标准**: 六项检查逐项通过 + 治理方案（风险双列负责人 + 留痕 + HITL 分级）+ 灰度计划。

1. **六项逐查**
   - 完成标准: 评估过线/性能成本/安全权限/留痕追溯/应急回滚/运营交接逐项有结论。
2. **配治理双列负责人**
   - 完成标准: 五类风险各有客户决策人 + FDE 对口人。
3. **设 HITL 三级**
   - 完成标准: 花钱/高风险动作执行前确认，只读放开；升级靠采纳率+兑现率数据。
4. **灰度上线**
   - 完成标准: 小流量低风险场景跑一两周，有放量节奏。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还没定义「好」、没建评估集——那是 eval-driven 的职责
- 还在做 demo——那是 demo-driven 的职责
- 只做内部工具、无企业级合规诉求——六项按需裁剪

### 作者在书中警告的失败模式

- 「跳过硬化阶段」：demo 通过后跳过边界/监控/压测/回滚，省下的时间在首次故障时用信任加倍还回。
- 「检查点设多了审批疲劳、设少了错误累积」——HITL 的平衡点在分层，不是越多越好。

### 作者的盲点 / 时代局限

- 采纳率/兑现率的放权达标阈值作者未给，只强调「更长窗口、更多样本上稳定」——需自行设定并声明。

### 容易混淆的邻近方法论

- 「治理即产品」：在强监管行业治理是入场券和核心竞争力，不是成本——本卡的治理方案在金融/政企场景应作为可报价能力，而非应付检查的负担。
