# 服务陷阱（a16z 四条件 + 毛利换护城河）

## R — 原文 (Reading)

> 我会看三条边界：总毛利能不能持续增长，同类项目的交付成本能不能下降，公司的现金能不能撑到毛利回升的转折点。
>
> — 曹犟，第 16 讲

## I — 方法论骨架 (Interpretation)

服务陷阱不是一次错误决策，而是「客户专属工作一点点跑赢通用平台工作」的渐进滑落。两套判断工具：

**a16z 重服务四条件**（判断业务值不值得用重服务换护城河）：①问题够不够关键；②客户够不够集中；③客户间有无共同模式；④场景有无足够强的数据/集成/监管门槛。四个条件大多不成立时，重服务从一开始就不成立。

**毛利换护城河三边界**（关键在「换」字）：①总毛利能否持续增长；②同类项目交付成本能否下降；③现金能否撑到毛利回升转折点。让出去的毛利必须换回三样——可复用产品能力、客户的数据入口、成为客户日常工作离不开的系统。

配套**三条纪律**：提前设置交棒条件（已验证的实施动作交出去，探索/标准/反馈/数据入口留在手里）；把不同性质 FDE 投入分开算（探索/重复交付/通用平台各看换回什么）；把毕业机制放进经营仪表盘（交付变轻 + 护城河变深两组指标）。

## A1 — 应用示例 (Application Example)

### 示例 1：服务陷阱（反例）
- **类型与来源**: 原书反例，第 16 讲
- **问题/输入**: 公司在一个个看似合理的决策中逐步滑向服务化
- **方法论的使用**: 用三边界反查——客户专属工作跑赢通用平台工作，毛利从软件七八成滑向服务四五成，且没换回可复用资产
- **结论**: 把产品公司做成「带软件估值倍数的昂贵服务公司」
- **结果**: 未说明（作为失败模式）

### 示例 2：毛利换护城河（转述，ServiceNow/Workday/Palantir）
- **类型与来源**: 原书转述，第 16 讲
- **问题/输入**: 重服务公司如何走通「先低后高」毛利曲线
- **方法论的使用**: 毛利暂时让出，但换回可复用产品能力+数据入口+工作系统，盯三条边界
- **结论**: 转折点=定制开始毕业 + 重复实施交给客户或伙伴 + 工作系统黏性体现
- **结果**: ServiceNow/Workday/Palantir 均走「先低后高」曲线

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 公司越做越像「项目公司」，毛利持续下滑
2. 要判断「这个重服务模式值不值得做」
3. 想用毛利换护城河，但不确定换回的东西值不值
4. 老板问「我们是不是在滑向外包」

### 语言信号 (用户的话里出现这些就应激活)

- 「怎么避免服务陷阱」「重服务值不值得做」「毛利换护城河」
- 「a16z 四条件」「怎么判断产品公司还是外包公司」「交付成本能不能下降」
- 英文: "service trap", "gross margin", "moat", "heavy services", "productization"

### 与相邻 skill 的区分

- 与 `pricing-ola-raas` 的区别：本卡是「经营层防滑向外包」，pricing 是「单项目怎么收费」——定价方式会影响是否会滑向服务陷阱。
- 与 `sediment-pipeline` 的区别：本卡是「经营判断」，sediment-pipeline 是「沉淀机制」——沉淀是防服务陷阱的抓手。

## E — 可执行步骤 (Execution)

**必需输入**: 客户集中度、客户间共同模式、毛利数据、交付成本趋势、现金储备。缺「交付成本趋势」时先拉同类项目的历史交付成本数据，不凭感觉判断。

**交付物与完成标准**: 一个「值不值得做重 / 是否已滑向服务陷阱」的判断 + 三条边界监控 + 交棒计划。

1. **过 a16z 四条件**
   - 完成标准: 四条件逐项判断（问题关键/客户集中/共同模式/门槛），大多不成立则重服务不成立。
2. **盯三条边界**
   - 完成标准: 总毛利增长、交付成本下降、现金撑到转折点，三边界有数据监控。
3. **核「换」回什么**
   - 完成标准: 让出的毛利换回可复用能力/数据入口/工作系统三样，而非只换回人力。
4. **设交棒条件 + 毕业仪表盘**
   - 完成标准: 已验证的实施动作有交棒条件；毕业机制进经营仪表盘。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 判断单个项目该不该接——那是 intake-gate 的职责
- 要建立沉淀机制——那是 sediment-pipeline 的职责
- 公司无重服务投入、纯 SaaS——服务陷阱的前提不成立

### 作者在书中警告的失败模式

- 「服务陷阱」：一次次「看似合理」的决策（这个客户很重要、这个定制不做就丢单）累积成毛利从软件滑向服务。

### 作者的盲点 / 时代局限

- 毛利「先低后高」曲线依赖 AI 持续降低交付成本这一假设，若模型能力进入平台期，交付成本下降曲线可能走平。

### 容易混淆的邻近方法论

- 与「真假 FDE 判断」的「复利」硬线是同一逻辑的公司级表达：个人/岗位看「第二个客户是否更容易」，公司看「交付成本是否下降」。
