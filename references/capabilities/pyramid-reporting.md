# 汇报金字塔 + MECE

## R — 原文 (Reading)

> 就是金字塔原理。结论先行，先用一句话说清结果，再给两三条理由，最后才是证据和细节。……还有一个配套原则，叫 MECE，中文意思是相互独立、完全穷尽。
>
> — 曹犟，第 7 讲

## I — 方法论骨架 (Interpretation)

向高管汇报，高管的注意力是最稀缺的资源，先亮结论才有资格占用后续时间。结构是金字塔：**结论先行**（一句话说清结果）→ **两三条理由** → **证据细节**。几条理由之间要 **MECE**——相互独立（不重叠）、完全穷尽（合起来不漏事实）。

同一座金字塔对不同对象讲到不同深度：电梯里讲塔尖（结论）、周会上讲到第二层（理由）、技术评审才下沉到细节。面对非技术决策者，必须把技术语言翻译成业务语言，而且只能 FDE 自己干——你不翻译，别人会替你翻译，翻译错的代价仍算在你头上。本质是「像设计接口一样设计表达，不冗余不遗漏」。

## A1 — 应用示例 (Application Example)

### 示例 1：向 CIO 汇报 demo 结果（合成演练，规则可复算）
- **类型与来源**: 原书给出结构、未给完整汇报实录，以下为合成演练
- **问题/输入**: 本周围绕「缺陷验证」跑通了端到端 demo，要向 CIO 汇报
- **方法论的使用**: 结论先行（本周围绕缺陷验证跑通端到端）→ 两条 MECE 理由（价值验证 ✓、技术风险可控 ✓）→ 细节后置
- **结论**: 塔尖→理由→证据的三层结构，CIO 能在电梯里就听懂结果
- **结果**: 合成演练输出，非作者经历

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 要给高管/客户决策层汇报项目进展或结论
2. 汇报时信息量太大，对方没耐心听完
3. 被要求「用一句话说清你到底要什么」
4. 想把技术方案讲给非技术的老板/客户听

### 语言信号 (用户的话里出现这些就应激活)

- 「怎么跟老板汇报」「结论先行怎么组织」「跟 CIO 讲这个方案怎么说」
- 「汇报被说太啰嗦」「怎么把技术翻译成业务语言」
- 英文: "pyramid principle", "executive summary", "conclusion first", "MECE", "how to report to leadership"

### 与相邻 skill 的区分

- 与 `stakeholder-map` 的区别：stakeholder-map 决定「对谁说、他在意什么」，本卡决定「说的内容怎么组织」。
- 与 `demo-driven` 的区别：demo-driven 是「做出来给人看」，本卡是「把结果讲清楚」——demo 的结论需要本卡来组织成汇报。

## E — 可执行步骤 (Execution)

**必需输入**: 要汇报的事实/结果 + 汇报对象是谁（决定讲到第几层）。缺「汇报对象」时先问「听的人是谁、有多少时间」，不默认讲满。

**交付物与完成标准**: 一份按「结论→理由→证据」组织的汇报，理由 MECE（不重叠、不遗漏），深度匹配对象。

1. **写结论（塔尖）**
   - 完成标准: 一句话说清结果，业务语言、非技术黑话。
2. **列两三条理由（第二层）**
   - 完成标准: 理由间 MECE——逐条检查无重叠、合起来无遗漏。
3. **备证据细节（底层）**
   - 完成标准: 每一条理由有支撑细节，但按对象控制是否下沉。
4. **按对象定深度**
   - 完成标准: 电梯讲塔尖、周会讲理由、技术评审才到细节。
5. **翻译技术语言**
   - 完成标准: 非技术决策者能听懂；技术语言已由你自己翻成业务语言。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还在判断谁是关键干系人、谁在意什么——那是 stakeholder-map 的职责
- 还没有可汇报的结论/结果——先去把事做出来（demo-driven / 施工 / 评估）
- 纯事实查询类回答——不需要金字塔组织

### 作者在书中警告的失败模式

- 不翻译技术语言，别人替你翻译、翻译错代价仍算你头上。
- 理由重叠或遗漏（不 MECE），会显得思路不清、浪费高管注意力。

### 作者的盲点 / 时代局限

- 汇报结构是「乙方对甲方高管」的默认假设，对内部汇报/同级协作的适用性作者未展开，需自行判断深度与形式。

### 容易混淆的邻近方法论

- 与「干系人地图四问」里的「他需要知道什么」是配套关系：地图决定「该让他知道什么」，金字塔决定「怎么把该知道的讲清楚」。
