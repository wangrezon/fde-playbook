# 施工纪律：gap 四象限 + 代码三区

## R — 原文 (Reading)

> 第一个区，这家客户的部署实例深处，我叫它负债区。……第二个区，feature flag 和配置层，我叫它隔离区。……第三个区，平台层，我叫它资产区。……写在哪，决定这行代码是资产还是负债。
>
> — 曹犟，第 9 讲

## I — 方法论骨架 (Interpretation)

在别人家的地基上施工，纪律比速度重要。两个配套的判断工具：

**gap 四象限**：先把产品与客户需求的差距列清单，用「通用/特有」×「阻塞/增强」两个问题定位：通用又阻塞→做进平台层；特有又阻塞→做进隔离层；通用不阻塞→平台提交统一排期；特有又不阻塞→延后或明确不做。每填一个 gap 都多问一句「这个能力能不能长回产品里」。

**代码三区**：代码写在哪决定它是资产还是负债——**负债区**（客户部署实例深处写死单客户逻辑，短期最快长期最贵）、**隔离区**（进统一代码库用 feature flag 管住，随版本走）、**资产区**（抽象成通用能力进平台）。

施工纪律是两句：别把特殊逻辑写死进负债区；也别把伪装成通用需求的特殊逻辑硬塞进资产区。

## A1 — 应用示例 (Application Example)

### 示例 1：神策「一套代码打天下」的代价（作者亲历，反例）
- **类型与来源**: 原书亲历，第 9 讲
- **问题/输入**: 长期把本该进隔离区的单客户特殊逻辑硬塞进资产区（产品主干）
- **方法论的使用**: 用「代码三区」反查——违反了「别把伪装成通用需求的特殊逻辑硬塞进资产区」
- **结论**: 产品越来越臃肿、迭代越来越难，单客户高价值需求反而无法响应
- **结果**: 此后引入 feature flag、大力开发 OpenAPI、加强定开制品管理来纠正

### 示例 2：跨账号对比报表（合成演练，规则可复算）
- **类型与来源**: 原书未提供完整案例，以下为合成演练
- **问题/输入**: 某客户要一个「跨账号对比」报表，口径只有这家客户有此需求
- **方法论的使用**: gap 判断「特有 + 阻塞」→ 放隔离区（feature flag + 配置层），既不写死负债区也不硬塞资产区
- **结论**: 升级随版本走，不产生人肉对齐成本
- **结果**: 合成演练输出，非作者经历

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 客户提了个性化需求，不知道该写进产品还是单独写死
2. 代码库越来越乱、升级要人肉对齐，想搞清楚问题出在哪
3. 判断某个需求「能不能长回产品」
4. 团队用 AI 飞快写定制代码，担心欠下技术债

### 语言信号 (用户的话里出现这些就应激活)

- 「这个需求写在哪」「负债区隔离区资产区怎么分」「gap 四象限」
- 「客户个性化需求要不要进产品」「怎么避免代码越来越臃肿」
- 英文: "code placement", "debt vs asset", "feature flag", "gap quadrant", "technical debt"

### 与相邻 skill 的区分

- 与 `integration-migration` 的区别：本卡是「需求/代码写在哪」，后者是「怎么接线、迁移、对账」。
- 与 `versioning-discipline` 的区别：本卡管「代码位置」，后者管「版本节奏」——负债区是版本分裂的源头，两者配套。
- 与 `sediment-pipeline` 的区别：本卡管「施工时的代码落位」，后者管「把可复用能力正式提交回平台」。

## E — 可执行步骤 (Execution)

**必需输入**: 产品与客户需求的 gap 清单（或一个具体新需求）。缺「这条 gap 是通用还是特有」判断时，先问「下一个客户会不会也有」，不凭感觉归类。

**交付物与完成标准**: 每个 gap 的四象限归类 + 对应打法 + 代码落位决策（负债/隔离/资产）。

1. **列 gap 清单**
   - 完成标准: 每个需求都问过「通用还是特有、阻塞还是增强」。
2. **四象限定位打法**
   - 完成标准: 每个 gap 落入四象限之一，配对应打法（平台层/隔离层/平台提交/延后）。
3. **定代码落位**
   - 完成标准: 明确写进负债区/隔离区/资产区，遵守两句纪律。
4. **多问一句「能不能长回产品」**
   - 完成标准: 每个 gap 都有「可产品化 or 明确不做」的结论。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还在选场景/做 demo——那是 use-case-prioritization / demo-driven 的职责
- 需求已判定可产品化、要正式提交——那是 sediment-pipeline 的职责
- 纯新功能的产品设计、不涉及客户特殊逻辑——本卡针对「客户 gap」而非「产品 roadmap」

### 作者在书中警告的失败模式

- 「每客户雪花化」：每个客户单独雕琢一套，项目间零复用，从赚钱变亏本。
- 「一套代码打天下」矫枉过正：害怕定制负债，把每个客户的个性化需求都做成产品功能，产品复杂度失控。

### 作者的盲点 / 时代局限

- AI 让写定制代码飞快，负债区诱惑更大——「AI 写得再快它也还是负债，只是欠债速度变快」。本卡约束的是「写在哪」，但不阻止「用 AI 快速产出」，需警惕用速度掩盖落位错误。

### 容易混淆的邻近方法论

- 「隔离区」与「资产区」容易混：隔离区是「开关管住的特殊逻辑」，资产区是「抽象成的通用能力」。伪装成通用需求的特殊逻辑硬塞资产区，正是神策踩过的坑。
