# demo 驱动开发（MVP + MVA + 每周 demo）

## R — 原文 (Reading)

> MVP 是最小可行产品……面向客户，证明这件事有价值；MVA 是最小可行架构……面向工程团队，验证那些决定方案能不能落地的核心技术风险是否可控。前者回答"值不值得做"，后者回答"做不做得成"。
>
> — 曹犟，第 8 讲

## I — 方法论骨架 (Interpretation)

demo 的最小单元要「宁可窄，不能断」——跑通端到端一条线，而不是铺十张半成品界面。一个最小单元同时完成两种验证：

- **MVP**（最小可行产品）：对外验证价值，回答「值不值得做」；
- **MVA**（最小可行架构）：对内验证技术可行性，回答「做不做得成」。MVA 不是一次性脚手架，是能毕业进生产架构的种子。

**每周 demo** 是把模糊反馈逼成具体工单的逼迫机制：每次给干系人演示一个运行中的系统，把「感觉不太对」逼成「审批人名字放第一列」这种可排期的工单。每次记三样：当场具体反馈（变工单）、没说出口的迟疑、双方承诺（落到具体人和时间）。演示时反复问「要怎样你才会点同意」，把讨论从「你觉得怎么样」拉到「距离验收还差什么」。

## A1 — 应用示例 (Application Example)

### 示例 1：端到端最小单元（作者亲历方法论）
- **类型与来源**: 原书亲历方法论，第 8 讲
- **问题/输入**: 客户要一个「数据报表」，十张报表都想做
- **方法论的使用**: 选定一张最有代表性的报表，从取数、配置、计算、可视化到产出结论完整跑通一条线
- **结论**: 窄但通，客户感受「这事能成」；宽而断，客户只记住「到处都是半成品」
- **结果**: 未说明（作为方法示范）

### 示例 2：demo 债务螺旋（反例）
- **类型与来源**: 原书反例，第 18 讲
- **问题/输入**: 团队用生产系统撑不住的 demo 拿下客户
- **方法论的使用**: 用本卡「demo 赢的是继续往下走的资格，不是合同」反查——把资格当合同，欠下 demo 债务
- **结论**: 此后每次沟通都在填「期望债」，交付进度停滞
- **结果**: 未说明（作为失败模式）

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 刚选定场景，要做出第一个 demo 给客户看
2. demo 做了很久，客户反馈一直「还行」但项目没进展
3. 不知道 demo 该做多宽、多深才够
4. 客户反馈太模糊，不知道怎么把它变成可执行的工单

### 语言信号 (用户的话里出现这些就应激活)

- 「第一个 demo 怎么做」「MVP 和 MVA 什么区别」「demo 该做多宽」
- 「客户反馈太模糊怎么办」「每周 demo 记录什么」「怎么逼客户给具体反馈」
- 英文: "MVP vs MVA", "demo driven development", "weekly demo", "minimum viable"

### 与相邻 skill 的区分

- 与 `use-case-prioritization` 的区别：后者决定「做哪个场景」，本卡决定「选定场景后怎么 demo 验证」。
- 与 `eval-driven` 的区别：本卡是「demo 阶段」验证价值与可行性，eval-driven 是「开发阶段」先定义「好」再用评估集驱动。
- 与 `go-live` 的区别：本卡到 demo 为止，go-live 是「硬化 + 上生产」的后半程。

## E — 可执行步骤 (Execution)

**必需输入**: 已选定的场景 + 一条可端到端跑通的最小业务流。缺「可运行 demo」或「反馈周期」时，先回到 intake-gate 的客户四问确认反馈周期，否则每周 demo 退化成每周汇报。

**交付物与完成标准**: 一个端到端 demo（MVP+MVA 双验证）+ 每周一页纸记录（反馈/迟疑/承诺）+ 具体工单。

1. **定最小单元（宁可窄不可断）**
   - 完成标准: 明确一条端到端业务流，从输入到结论完整、可演示。
2. **做 MVP（验价值）**
   - 完成标准: 客户能看到「这事能成」，产出具体结果而非半成品。
3. **做 MVA（验可行性）**
   - 完成标准: 承重技术风险（模型能力/数据工具接通/规模成本兜底）有验证结论。
4. **每周 demo + 记三样**
   - 完成标准: 当场反馈变工单、迟疑被记录、承诺落到人和时间；持续追问「要怎样你才点同意」。
5. **反馈闭环**
   - 完成标准: 模糊反馈全部转化为可排期工单，无「感觉不太对」悬空。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 场景优先级还没定——那是 use-case-prioritization 的职责
- demo 已通过、要上生产——那是 go-live 的职责
- 纯后端/无客户可见结果的内部工具——「运行中的系统作为共同事实」的前提不成立

### 作者在书中警告的失败模式

- 「demo 债务螺旋」：用生产系统撑不住的 demo 拿下客户，此后反复还「期望债」。
- 「demo 赢合同幻觉」：demo 赢的是「继续往下走的资格」，不是合同；把资格当合同就提前欠债。
- 「跳过硬化阶段」：demo 通过后跳过边界/监控/压测/回滚，省下的时间在首次故障时用信任加倍还回。

### 作者的盲点 / 时代局限

- 模型非确定性让 AI 产品「demo 到可用」的鸿沟比传统软件更宽，作者强调但未给「demo 通过到硬化」的量化判据。

### 容易混淆的邻近方法论

- MVP 与 MVA 必须成对出现：只做 MVP 不做 MVA，demo 惊艳但架构纸糊、第四个月重写。
