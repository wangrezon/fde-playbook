# 客服授权三级 + 降级

## R — 原文 (Reading)

> 客服 Agent 的能力可以分成三级：答得准、能动手、敢托付，一级比一级价值高，也一级比一级难。……每上一级，护栏和审计就要加一层。
>
> — 曹犟，第 21 讲

## I — 方法论骨架 (Interpretation)

客服/零售行业直接驱动业务，Agent 授权分三级：

1. **答得准**：核心指标是拦截率（用户问题被 AI 直接解决、不再转人工的比例），知识管理是难点；
2. **能动手**：调用订单/物流等业务系统，但仍由人做决定、Agent 负责执行（改地址先展示确认、补发由人工批准）；
3. **敢托付**：在规则和额度范围内把有限业务判断权 + 执行权一起交给 Agent，只有异常转人工（退款/赔付/改签）。

铁律：每上一级，护栏和审计加一层。拦截率两个注意：不能单独看（需与满意度、转人工后解决率一起观察）；要看统计口径（分母是否含自助解决会话、先问 AI 再转人工算哪边），承诺前先写清算法。**降级机制要提前设计**：满意度/投诉率/转人工需求持续恶化就缩小 Agent 自主范围交回真人。放权节奏由数据而非意愿决定。

## A1 — 应用示例 (Application Example)

### 示例 1：Klarna AI 客服降本过头（转述）
- **类型与来源**: 原书转述，第 21 讲
- **问题/输入**: Klarna AI 客服覆盖 23 市场、首月处理 230 万次对话、解决时间从 11 分钟降到 2 分钟
- **方法论的使用**: 用降级机制反查——效率之外，客服始终有一部分情绪价值只能由真人提供
- **结论**: 2025 年 5 月 Klarna CEO 表示降本走得太远、要重新增加真人客服
- **结果**: 降本过度后回补真人客服

### 示例 2：Decagon 自动退款（转述）
- **类型与来源**: 原书转述，第 21 讲
- **问题/输入**: Decagon 客服 Agent 在用户申请退款时，先查退款资格再调支付系统完成退款
- **方法论的使用**: 第三级「敢托付」的形态——Agent 在规则内自主判断并执行
- **结论**: 公开材料未披露额度上限、人工检查点与降级机制，是护栏未透明的风险点
- **结果**: 未说明（额度/检查点/降级机制未披露）

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 要设计一个客服 Agent 的授权边界
2. 客服 Agent 该不该自动退款/赔付，拿不准
3. 客服 AI 的拦截率指标怎么定、怎么不误读
4. 客服 Agent 表现下滑，要设计降级机制

### 语言信号 (用户的话里出现这些就应激活)

- 「客服 Agent 怎么分级授权」「答得准能动手敢托付」「拦截率怎么算」
- 「该不该自动退款」「降级机制怎么设计」
- 英文: "customer service agent", "authorization levels", "containment rate", "escalation"

### 与相邻 skill 的区分

- 与 `go-live` 的区别：本卡是「客服业务授权等级」，go-live 是「通用上生产检查」——本卡是 go-live 的 HITL 在客服场景的具体化。
- 与 `safety-guardrails` 的区别：本卡是「业务授权阶梯」，safety-guardrails 是「数据/操作安全护栏」——后者是前者的技术底座。
- 与 `industrial-rule-model` 的区别：本卡对应零售/客服，后者对应制造/能源。

## E — 可执行步骤 (Execution)

**必需输入**: 客服 Agent 要承担的动作清单 + 满意度/投诉/转人工数据。缺「动作清单」时先枚举 Agent 所有动作（退款/改地址/补发等）。

**交付物与完成标准**: 一套客服授权分级方案（三级各配动作）+ 拦截率口径 + 降级机制。

1. **分级授权**
   - 完成标准: 每个动作归入「答得准/能动手/敢托付」之一，敢托付的动作在规则+额度内。
2. **定拦截率口径**
   - 完成标准: 拦截率与满意度、转人工后解决率一起看；统计口径（分母）书面化。
3. **每上一级加护栏审计**
   - 完成标准: 每升级一级，护栏和审计同步加一层。
4. **设计降级机制**
   - 完成标准: 满意度/投诉率/转人工需求持续恶化即缩小自主范围交回真人。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 要配置数据/操作安全护栏——那是 safety-guardrails 的职责
- 要过整体上生产检查——那是 go-live 的职责
- 制造/能源类「规则/模型划界」——那是 industrial-rule-model 的职责

### 作者在书中警告的失败模式

- Klarna 教训：降本走太远，效率之外客服的情绪价值只能由真人提供，降本过度要回补真人。
- 拦截率单独看会误判，必须与满意度、转人工后解决率一起观察。

### 作者的盲点 / 时代局限

- 公开案例（Decagon）未披露额度上限/检查点/降级机制，作者据公开材料判断「敢托付形态已出现」，但护栏透明性存疑。

### 容易混淆的邻近方法论

- 「敢托付」≠「全放权」：是在规则和额度范围内的有限业务判断权+执行权，异常仍转人工，放权节奏由数据而非意愿决定。
