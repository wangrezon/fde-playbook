# 评估驱动开发

## R — 原文 (Reading)

> 第一步，和客户一起把"好"的标准写下来……第二步，把这些标准变成一条条可以跑的实际用例，构建评估集。第三步，搭好 harness。第四步，开始写 prompt、搭 Agent。
>
> — 曹犟，第 11 讲

## I — 方法论骨架 (Interpretation)

AI 项目把传统「PRD→实现→测试」顺序倒过来：**先定义「好」，再写第一行 prompt**。

四步：①和客户一起把「好」的标准写下来（什么算对/错/不能说）；②把标准变成可跑的评估用例，构建评估集；③搭 Harness（模型之外的一切控制机制，Agent = Model + Harness）；④才开始写 prompt、搭 Agent。

评估集分三类：**黄金集**（核心场景该对的一直对，对错能程序判定）、**异常场景集**（「奇怪的星期二」等 corner case）、**安全对抗集**（故意设套测边界，测它知不知道何时不能回答）。上线标准各不同：黄金集接近满分、异常集不低于上一版、安全对抗集一条不过就停。

**棘轮原则**：分数每上一个台阶就成为新地板，任何改动不许打回地板以下；补用例可随时补，改期望值必须慎重且让客户知情（改期望=重新定义「好」，考不过就改考卷是自己骗自己）。**评估面/客户面分工**：系统质量标准、评估集维护、回归纪律归 FDE；业务口径、结果价值、最终验收归客户。

## A1 — 应用示例 (Application Example)

### 示例 1：Anthropic 帮 Lyft / ServiceNow（转述）
- **类型与来源**: 原书转述，第 3 讲
- **问题/输入**: 帮 Lyft 做客服助手、帮 ServiceNow 做销售准备
- **方法论的使用**: 先花一周做十几场用户访谈、嵌进业务，第二周设计评估，随后几周搭系统、灰度上线
- **结论**: 「先定义好再写 Prompt」的节奏可复制
- **结果**: Lyft 客服解决时间降 87%+，ServiceNow 销售准备时间缩短 95%

### 示例 2：「考不过就改考卷」（反例）
- **类型与来源**: 原书反例，第 11 讲
- **问题/输入**: 评估用例跑不过，团队把期望值改低让分数好看
- **方法论的使用**: 用棘轮原则反查——改期望=重新定义「好」，尺子已弯
- **结论**: AI 项目里最容易发生也最难被发现的腐化

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 要开始一个 AI 项目，不知道从哪写起
2. 客户问「怎么保证 AI 系统质量」
3. 上线后说不清系统「变好还是变坏」
4. 团队在「调 prompt」和「建评估」之间纠结优先级

### 语言信号 (用户的话里出现这些就应激活)

- 「AI 项目怎么定义好」「评估集怎么建」「先写 prompt 还是先建评估」
- 「黄金集异常集安全对抗集」「棘轮原则」「怎么验收 AI」
- 英文: "eval-driven development", "golden set", "eval set", "ratchet principle", "harness"

### 与相邻 skill 的区分

- 与 `demo-driven` 的区别：demo-driven 是「demo 阶段验价值/可行性」，本卡是「开发阶段用评估集驱动」。
- 与 `go-live` 的区别：本卡的评估集是 go-live 六项检查里第一项「评估过线」的来源。
- 与 `knowledge-layering` 的区别：本卡管「怎么定义好」，后者管「喂什么知识」。

## E — 可执行步骤 (Execution)

**必需输入**: 业务场景 + 客户（用于共建「好」的标准）。缺「客户参与」时，先明确哪些口径客户说了算，不越界替客户定业务口径。

**交付物与完成标准**: 一套评估集（黄金/异常/安全对抗三类）+ Harness + 按评估驱动的 Agent。

1. **共建「好」的标准**
   - 完成标准: 与客户写清什么算对/错/不能说。
2. **建三类评估集**
   - 完成标准: 黄金集（可程序判定）、异常集（corner case）、安全对抗集（守边界）各有用例。
3. **搭 Harness**
   - 完成标准: 模型之外的控制机制（环境/工具/护栏/上下文/输出验证）就位。
4. **写 prompt、搭 Agent**
   - 完成标准: 每次改动跑全量评估，棘轮原则生效（分数只进不退）。
5. **划评估面/客户面**
   - 完成标准: 工程标准归 FDE、业务口径归客户，分工书面化。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还在做 demo 验价值——那是 demo-driven 的职责
- 已经定义好「好」，要过整体上线检查——那是 go-live 的职责
- 非 AI 项目（无模型输出需评估）——传统测试流程即可

### 作者在书中警告的失败模式

- 「考不过就改考卷」：跑不过就调低期望，是 AI 项目最常见、最难发现的腐化，尺子一弯评估就失去意义。

### 作者的盲点 / 时代局限

- Harness 组件清单作者仅引用 Martin Fowler 定义、未展开，需自行补充具体组件。
- 「先定义好」假设业务口径可谈清，但复杂业务里「好」本身可能随迭代变化，需在棘轮原则下管理「改期望」的频率。

### 容易混淆的邻近方法论

- 评估集 ≠ 传统测试用例：评估集是「开发迭代的方向盘」，且要在写第一行 prompt 之前先建，位置不同决定整套逻辑。
