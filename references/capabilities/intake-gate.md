# 进场前判断：立项四问 + 客户四问

## R — 原文 (Reading)

> 在进场之前，你至少要把四个问题问清楚：这件事在客户那边，有没有一个真正说了算的负责人？有没有真实的预算？用什么指标衡量成功？还有最关键的一条，这个项目有没有明确的退出条件？
>
> — 曹犟，第 5 讲

## I — 方法论骨架 (Interpretation)

进场前先用两道关把「该不该接」判断清楚，避免一头扎进填不完的需求里。

**立项关（四问）**筛「项目值不值得做」：①有没有真正说了算的决策人；②有没有真实预算；③用什么指标衡量成功；④最关键——有没有明确退出条件。没有退出条件的项目不是项目，是「无底洞式的支持合同」。

**客户关（四问）**筛「组织接不接得住 FDE」：①有没有有分量、愿带你进业务会议的人；②真实数据和权限给不给；③反馈周期多长；④谁为探索买单。四问里只要有明确否定答案，就别硬进场——接不住的客户用传统交付反而更好。

两关合起来回答同一个问题：这是「做产品探索」还是「填需求无底洞」。

## A1 — 应用示例 (Application Example)

### 示例 1：无退出条件的项目（反例）
- **类型与来源**: 原书反例，第 5 讲
- **问题/输入**: 一个客户有预算、有负责人，但合同里没写「什么算成功、什么时候算结束」
- **方法论的使用**: 过立项四问，第四问「退出条件」直接命中否
- **结论**: 判为「无底洞式支持合同」，不接，或先补退出条款再进场
- **结果**: 未说明（作为规则论证）

### 示例 2：客户反馈周期过长（合成演练，规则可复算）
- **类型与来源**: 原书未提供完整案例，以下为按客户四问规则做的合成演练
- **问题/输入**: 客户有带进业务会议的人、愿给只读数据，但每次反馈要过三级审批、周期两周
- **方法论的使用**: 过客户四问，第三问「反馈周期」命中「过长」
- **结论**: 判定「接不住 FDE 的迭代方式」——反馈要过几层审批，每周 demo 的迭代优势归零，改用传统交付或先谈反馈通道
- **结果**: 合成演练输出，非作者经历

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 拿到一个新客户/新项目的进场机会，不确定该不该接
2. 销售签了单，交付团队要评估这单会不会是坑
3. 已经在项目里被拖了半年，反思「当初进场前漏问了什么」
4. 老板问「这个客户我们接不接」，需要结构化判断依据

### 语言信号 (用户的话里出现这些就应激活)

- 「这个项目该不该接」「进场前要问清楚什么」「怎么判断客户靠不靠谱」
- 「这单会不会是无底洞」「没有退出条件怎么办」
- 英文: "should we take this deal", "pre-sales qualification", "exit criteria", "customer fit"

### 与相邻 skill 的区分

- 与 `genuine-check`（真假 FDE）的区别：本卡判断「这一单项目」，genuine-check 判断「这个岗位/团队」。
- 与 `five-day-discovery`（五天摸真问题）的区别：本卡是「进不进场」的闸门，five-day-discovery 是「进场之后怎么摸」。
- 与 `service-trap` 的区别：本卡是单项目入场判断，service-trap 是公司级长期经营判断。

## E — 可执行步骤 (Execution)

**必需输入**: 目标项目的基本事实——决策人是谁、预算是否真实、成功指标、退出条件；客户侧是否有人带进业务会议、数据权限、反馈周期、谁为探索买单。缺失任一项时先问，不臆断。

**交付物与完成标准**: 一份「接 / 不接 / 带条件接」的结论 + 命中项清单 + 未满足项的补救方式。

1. **过立项四问**
   - 完成标准: 四问各有一个明确答案；「退出条件」一问没有明确答案即记 red flag。
2. **过客户四问**
   - 完成标准: 四问逐项打 ✓/✗；出现明确 ✗ 就标记「接不住 FDE」。
   - 判停条件: 任一关出现硬性否定（无退出条件 / 无业务会议引路人）→ 直接输出「不接或带条件」，跳到第 4 步。
3. **综合判断与补救**
   - 完成标准: 对未满足项给出补救（补退出条款 / 先谈反馈通道 / 先要只读数据）。
4. **输出结论**
   - 完成标准: 「接/不接/带条件接」+ 依据 + 补救项，落到书面。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 进场之后怎么摸清真问题——那是 five-day-discovery 的职责
- 判断团队是不是真 FDE——那是 genuine-check 的职责
- 已经签了合同、要评估是否止损——那是 failure-identification（项目级止损三条件）的职责

### 作者在书中警告的失败模式

- 「无退出条件的项目是支持合同不是项目」，会把团队拖成高级外包、越做越重、永远抽不出身（对应反例 ce20）。

### 作者的盲点 / 时代局限

- 整套方法默认「甲方愿意深度配合、愿意改变自己」。对甲方内部执行阻力、IT/业务不配合时怎么办，作者着墨较少——本卡的四问能筛出「接不住」的客户，但无法替甲方解决配合意愿问题。

### 容易混淆的邻近方法论

- 与「客户四问」里的「反馈周期」和每周 demo 的「反馈周期」是同一个约束在不同阶段的体现——本卡是进场前的预判，demo 是进场后的验证。
