# 干系人地图 + 怀疑者/赞助人管理

## R — 原文 (Reading)

> 把所有能影响项目命运的人写在一张表上，一个一个搞清楚四个问题：他能拍板什么？他能否决什么？他需要知道什么？以及最重要的，他真正在意什么？
>
> — 曹犟，第 7 讲

## I — 方法论骨架 (Interpretation)

技术价值必须先过「人」这一关。进场后尽早画出干系人地图：把所有能影响项目命运的人写真人真名（不写部门），逐个回答四问——拍板什么、否决什么、需要知道什么、真正在意什么（前三问是权力结构，第四问是动机，技术人最易忽略）。

再圈出三类人、三种打法：**能杀死项目的**（预算权力者）→ 低频高质量同步；**能拖延项目的**（安全/合规/采购把关人）→ 提前送料留足流程时间；**能放大项目的**（标杆用户）→ 重点服务让其先用出效果再宣传。

两个特殊角色单独处理：**怀疑者**——别说服、别绕开，给他一个真实角色（第一个测试者），把较真变成质检；**赞助人**——防「赞助人崩塌」，从一开始培养至少两个赞助人 + 尽快建立自下而上的真实使用习惯。

## A1 — 应用示例 (Application Example)

### 示例 1：IBM Watson 赞助人崩塌（转述，反例）
- **类型与来源**: 原书转述，第 18 讲
- **问题/输入**: MD 安德森项目四年投入 6200 万美元，2015 年核心赞助人 Lynda Chin 离职
- **方法论的使用**: 用本卡「赞助人防崩塌」规则反查——项目只挂一个赞助人、无第二支持者
- **结论**: 赞助人崩塌是项目失败的组织过程，而非技术本身被检验
- **结果**: 系统从未用于任何患者，项目进入审计

### 示例 2：怀疑者转化（合成演练，规则可复算）
- **类型与来源**: 原书给出方法、未给完整案例，以下为合成演练
- **问题/输入**: 安全负责人在评审会上明显反对，担心数据泄露
- **方法论的使用**: 第三条路——不试图说服，请他当第一个测试者，把系统中权限控制这一部分交给他用最挑剔的眼光测
- **结论**: 挑出的毛病认真修，较真从阻力变成质检
- **结果**: 合成演练输出（作者原书称怀疑者往往反转成最强内部拥护者）

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 新项目进场，不知道客户组织里谁是关键人物、谁说了算
2. 项目推进中总被某个部门卡住，想搞清楚「谁在拖延、为什么」
3. 项目唯一靠山可能要调岗/失势，担心项目说停就停
4. 团队里/客户方有人公开反对项目，不知道怎么办

### 语言信号 (用户的话里出现这些就应激活)

- 「怎么画干系人地图」「谁说了算」「谁能拍板谁能否决」
- 「项目被某部门卡住了」「怎么搞定反对的人」「赞助人会不会走」
- 英文: "stakeholder map", "who can kill this project", "win over skeptics", "executive sponsor"

### 与相邻 skill 的区分

- 与 `pyramid-reporting` 的区别：本卡是「搞清楚该影响谁」，后者是「怎么把结果说给关键人听」。
- 与 `intake-gate` 的区别：intake-gate 问「有没有说了算的人」（进场前），本卡进场后把「人」细化成地图。
- 与 `failure-identification` 的区别：本卡的「赞助人崩塌」是六种失败模式之一，failure-identification 是六种模式的完整体检。

## E — 可执行步骤 (Execution)

**必需输入**: 项目相关人名单（含自己公司内部角色）。缺「真实人名」时先通过业务会议/访谈补名字，不写「IT 部」「业务部」这种无信息量的占位。

**交付物与完成标准**: 一张干系人地图（四问 + 三类人标注）+ 怀疑者/赞助人专项动作。

1. **列名单写真名**
   - 完成标准: 每个影响项目命运的人都是真人真名，名字来自真实对话。
2. **逐个回答四问**
   - 完成标准: 拍板/否决/需知/在意四栏都填了，「在意什么」有具体动机（非泛泛「支持项目」）。
3. **圈三类人配打法**
   - 完成标准: 杀死/拖延/放大三类各有人名 + 对应同步/前置/重点服务打法。
4. **专项处理怀疑者与赞助人**
   - 完成标准: 怀疑者有正式角色；赞助人 ≥2 个 + 有自下而上使用习惯的推进动作。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还没进场、还在判断项目该不该接——那是 intake-gate 的职责
- 要排场景优先级——那是 use-case-prioritization 的职责
- 要写汇报材料结构——那是 pyramid-reporting 的职责

### 作者在书中警告的失败模式

- 「赞助人崩塌」：项目命运绑在一个人身上，他走项目就停（IBM Watson 教训）。
- 「接单员陷阱」：把赢得信任理解成顺从，来一个需求接一个，从专家降级成「一双好用的手」。
- 「永久拐杖」：客户永远离不开你，你也抽不出身，双输。

### 作者的盲点 / 时代局限

- 乙方视角：默认「甲方愿意配合、愿意改变自己」，对甲方内部政治阻力着墨偏少。本卡能帮你识别和布局，但无法替你消除组织政治本身。

### 容易混淆的邻近方法论

- 「怀疑者转化」（给角色）与「说服」（给理由）是两条相反的路——本卡明确反对后者，说服会变推销、绕开会让他暗中反对。
