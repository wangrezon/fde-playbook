# 五天摸真问题

## R — 原文 (Reading)

> 动作一：坐到真正的用户旁边去，画出真实的流程图。动作二：把自己当小白，亲手把这活干一遍。动作三：用合成数据搭个轻原型，去"挑逗"真实反应。动作四：专门去挖那些"没人主动说"的阻塞点。动作五：分清楚"真问题"和"客户的合理选择"。
>
> — 曹犟，第 5 讲

## I — 方法论骨架 (Interpretation)

进场第一周决定整个项目的走向。五个动作的核心是**别听客户怎么说，去看客户怎么做、亲手做一遍**：

1. 坐到真正的用户（不是主管）旁边，画出真实流程图；
2. 把自己当小白，亲手把这活干一遍（练出能跟用户顺畅对话的硬功夫）；
3. 用合成数据搭个轻原型丢到用户面前，逼出真实反应；
4. 专门挖「没人主动说」的阻塞点——别问「你们一般怎么做」，问「上周二下午三点你在忙什么」（奇怪的星期二）；
5. 分清真问题与客户的合理选择。

攒下的一堆「问题」再用五条标准筛：可衡量、用户亲历（非主管转述）、亲手验证过、排除了「客户的合理选择」、价值够大且能归因到你头上。五关全过才是值得投入的真问题。进场最大的两层陷阱是：把客户的「解决方案」当「问题」，把客户的「合理选择」当「bug」。

## A1 — 应用示例 (Application Example)

### 示例 1：投手排期偏移（作者亲历）
- **类型与来源**: 原书亲历，第 5 讲
- **问题/输入**: 驻场时投手逐屏讲广告排期设置
- **方法论的使用**: 动作四——挖阻塞点，顺口问具体时点事实，投手带出一句「排期开始时间不准，设了下午六点常要晚一两个小时」
- **结论**: 一件反复发生却从未写进 SOP 的「奇怪的星期二」被挖出
- **结果**: 成为作者总结「奇怪的星期二」问法的一手素材（未交代是否最终产品化）

### 示例 2：把客户的解决方案当问题（反例）
- **类型与来源**: 原书反例，第 5 讲
- **问题/输入**: 客户说「我要一个自动报表」
- **方法论的使用**: 穿过第一层陷阱——客户给的是他自想的方案，真正痛点可能是「跨账号横向对比数据」
- **结论**: 照做自动报表也解决不了横向看数据的痛点
- **结果**: 未说明（作为陷阱论证）

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 刚进驻一个新客户，面对「一堆需求」不知道从哪下手
2. 客户给了明确需求，但怀疑「这不是真问题」
3. 访谈做了几轮，还是觉得没摸到要害
4. 想建立「真问题」的判断标准，避免被带偏

### 语言信号 (用户的话里出现这些就应激活)

- 「怎么摸清客户真正的痛点」「进场第一周干什么」「客户说想要 X，但我觉得不对」
- 「这是不是客户的合理选择」「怎么挖出没人说的阻塞点」「奇怪的星期二」
- 英文: "discover real problem", "first week on-site", "customer's real pain", "strange tuesday"

### 与相邻 skill 的区分

- 与 `intake-gate`（立项四问）的区别：intake-gate 是「进不进场的闸门」，本卡是「进场后怎么摸」。
- 与 `translation-northstar`（翻译+北极星）的区别：本卡产出「真问题清单」，后者把真问题进一步翻译成「可衡量的结果 + 北极星指标」。本卡是上游。
- 与 `use-case-prioritization` 的区别：本卡是「发现问题」，后者是「对候选场景排序」。

## E — 可执行步骤 (Execution)

**必需输入**: 客户现场访问权 + 一个真实用户 + 动手做一遍的许可。缺「能坐到真实用户旁边」时，先回到 intake-gate 的「客户四问」确认有没有引路人，不硬做二手访谈。

**交付物与完成标准**: 一份「真问题清单」，每条都通过五标准（可衡量/亲历/已验证/排除合理选择/可归因）。

1. **坐旁边画真实流程图**（动作一）
   - 完成标准: 有用户亲自确认的流程图，而非主管转述的版本。
2. **亲手干一遍**（动作二）
   - 完成标准: 能独立完成一次该业务操作（如完整做一次上架），而非只看演示。
3. **合成数据挑逗**（动作三）
   - 完成标准: 轻原型得到用户的真实反应记录，而非礼貌性「挺好的」。
4. **挖阻塞点 + 分清真问题与合理选择**（动作四、五）
   - 完成标准: 每个候选问题都问过「你们为什么这么做」，标出「真问题」还是「客户 know-how」。
5. **过五标准筛真问题**
   - 完成标准: 每条真问题五关全过，写清可衡量的数字/业务结果。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 还没决定进不进场——那是 intake-gate 的职责
- 已经有了真问题、要选先做哪个场景——那是 use-case-prioritization 的职责
- 要评估一个岗位是不是真 FDE——那是 genuine-check 的职责

### 作者在书中警告的失败模式

- 两层陷阱：把客户的「解决方案」当「问题」（ce09）；把客户的「合理选择」当「bug」（ce10）——仗着懂技术懂通用方法，上来就把人家的业务 know-how 当错误改掉，不仅没解决问题还失去信任。

### 作者的盲点 / 时代局限

- 五天质量决定全局，但作者默认「客户愿意让你坐进现场、配合你动手」。对无法获得现场访问权的场景（远程、甲方抵触），五动作的可执行性会打折扣——需自行换算。

### 容易混淆的邻近方法论

- 「奇怪的星期二」问法（问具体时点）与普通流程访谈（问「一般怎么做」）是相反的问法——本卡要求前者，因为后者只能得到被整理过的标准流程。
