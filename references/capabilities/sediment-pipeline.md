# 沉淀管道（内环外环 + 平台提交 + 前后方握手）

## R — 原文 (Reading)

> 内环，是在客户现场把东西做出来的循环……外环，则是把单客户成果固化成产品或者说公司能力的循环。……每一次交付，都是给一个客户修一条碎石路；外环的工作，就是有节奏地判断哪些碎石路值得铺成柏油高速。
>
> — 曹犟，第 13 讲

## I — 方法论骨架 (Interpretation)

FDE 工作分两个环：**内环**在客户现场交付价值（进场→选场景→干系人→demo→施工→评估→上线），**外环**把单客户成果固化成通用产品能力。「内环让客户满意，外环让公司值钱」。只有内环没外环，复利为零，本质是套着软件外壳的咨询公司。

外环不能靠自觉，要有固定管道：

- **平台提交**：把现场可产品化问题结构化交给平台团队，四要素——现象（客户在什么场景遇到问题）、根因（本质上缺什么能力）、建议（抽象成什么形态）、受益面（还有哪些客户会用到）。区别于「转发客户原话」。
- **前后方握手**：FDE 团队与平台工程团队的固定周会，共同对需求 pipeline 负责，飞轮在此转起或卡住。

沉淀转得好不好，看三个数字 + 一个危险信号：第二客户时间（第二次交付比第一次快多少）、单位经济（第二次交付成本是否零头）、平台提交率（季度多少条现场学习变路线图功能）；危险信号是「平台仓库里客户专属代码比通用代码增长还快」。

## A1 — 应用示例 (Application Example)

### 示例 1：Palantir 空客沉淀出 Skywise（转述）
- **类型与来源**: 原书转述，第 1 讲
- **问题/输入**: Palantir 长期驻场空客工厂，啃出二十多个问题
- **方法论的使用**: 前半段内环解决单客户问题，后半段外环把空客成果沉淀成 Skywise 平台
- **结论**: 前线 Delta 探索 + 后方 Dev 沉淀的教科书式案例
- **结果**: Skywise 反向卖给整个航空业，接入一百多家航空公司

### 示例 2：咨询陷阱（反例）
- **类型与来源**: 原书反例，第 18 讲
- **问题/输入**: FDE 团队逐渐偏离产品化方向，做的是高端咨询
- **方法论的使用**: 用危险信号反查——平台仓库客户专属代码比通用代码长得快
- **结论**: 只有内环没外环，退化成「套着软件外壳的咨询公司」
- **结果**: 未说明（作为失败模式）

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要这个 skill?

1. 项目做完了，但成果没沉淀成产品能力，觉得「白做了」
2. 想建立「现场认知 → 产品路线图」的固定机制
3. 前端抱怨「产研不接需求」、产研抱怨「一线只转发原话」
4. 要评估沉淀做得好不好（第二客户时间、平台提交率）

### 语言信号 (用户的话里出现这些就应激活)

- 「怎么把客户成果沉淀成产品」「内环外环」「平台提交怎么写」
- 「前后方握手」「怎么防止只做一次性交付」「沉淀仪表盘」
- 英文: "sediment to product", "platform submission", "inner loop outer loop", "productization"

### 与相邻 skill 的区分

- 与 `code-placement` 的区别：本卡是「把可复用能力正式提交回平台」的管道，code-placement 是「施工时代码落位」。
- 与 `private-knowledge` 的区别：本卡沉淀的是「产品能力」（平台提交），private-knowledge 沉淀的是「知识资产」（四步转化）。
- 与 `autonomy-ladder` 的区别：本卡是「成果回产品」，autonomy-ladder 是「交接给客户」——一个对外环产品，一个对客户团队。

## E — 可执行步骤 (Execution)

**必需输入**: 现场发现的可产品化问题 + FDE/平台两支团队。缺「受益面」判断时先问「除了这家客户还有谁会用到」，不把单客户需求当通用能力提交。

**交付物与完成标准**: 平台提交文档（四要素）+ 前后方握手机制 + 项目沉淀清单。

1. **判断是否可产品化**
   - 完成标准: 每个现场问题都问过「有没有第二个客户会走这条路」。
2. **写平台提交（四要素）**
   - 完成标准: 现象/根因/建议/受益面四要素齐全，非转发客户原话。
3. **进前后方握手会**
   - 完成标准: 固定周期、共同对 pipeline 负责、有排期追踪。
4. **看沉淀仪表盘**
   - 完成标准: 第二客户时间/单位经济/平台提交率三个数字 + 危险信号有季度记录。

## B — 边界 (Boundary) ★

### 不要在以下情况使用此 skill

- 判断代码写在哪——那是 code-placement 的职责
- 沉淀「知识」而非「产品能力」——那是 private-knowledge 的职责
- 项目还没做完、还没到结项沉淀阶段——先走 demo/施工/上生产

### 作者在书中警告的失败模式

- 「咨询陷阱」：客户专属代码跑赢通用代码，交付的是高端咨询而非产品。
- 「每客户雪花化」：每个客户单独一套，项目间零复用。

### 作者的盲点 / 时代局限

- 「哪些现场认知真能抽象成跨客户通用能力」的判据偏经验化（「等第二个样本出现」），缺乏可复制的量化标准——本卡的「受益面」四要素能辅助判断，但不能完全消除这一不确定性。

### 容易混淆的邻近方法论

- 「平台提交」与「转发客户原话」是本质区别：前者转交学习成果（四要素），后者当传话筒。写平台提交是外环，转发原话是假沉淀。
