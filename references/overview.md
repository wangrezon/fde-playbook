## 1. 结构 (Structural)

### 类型

实操手册 + 行业方法论。一门面向 To B 交付从业者的「如何做 FDE」实战课，同时带有认知普及（是什么/为什么）和职业指南（怎么入行/怎么晋升）的完整闭环。

### 一句话主旨

当 AI 让「写代码」不再稀缺，真正稀缺的是把 AI 交付成客户的业务结果、再把现场认知沉淀回产品的能力——这正是 FDE（Forward Deployed Engineer，前向部署工程师）的核心价值，本课教的就是这件事怎么做。

### 骨架 (主要论点及其关系)

1. **认知篇（第 1–4 讲）**: FDE 是什么——一个「嵌入客户现场、主动交付有价值结果的产品探索者」；它与咨询/外包/驻场/售前的本质区别在「对什么结果负责」和「做完一单沉淀下什么」；为什么现在火（需求侧：95% 的 AI 项目零回报，交付成胜负手；供给侧：AI 让一个人能打穿全链路）；中国机会（十年没走通的交付难题 + 六道坎 + 窗口期）。
2. **进场与验证（第 5–8 讲）**: 项目生命周期前段——立项四问 + 客户四问、五天摸真问题（五个动作）、选对场景（北极星三条件 + 价值链 + 打分排序）、干系人与信任（干系人地图/怀疑者/赞助人/汇报/信任边界）、Demo-driven（MVP+MVA、每周 demo）。
3. **施工与上线（第 9–12 讲）**: 项目生命周期中段——填 gap 写生产代码（gap 四象限 + 代码三区 + 集成迁移 + 私有化版本纪律）、用 AI 放大交付守住数据安全红线（四层知识库 + 护栏五件套）、评估驱动开发（三类评估集 + 棘轮 + 评估面/客户面）、上生产（上线六项检查 + 五类治理风险 + 全链路留痕 + HITL）。
4. **沉淀与变现（第 13–16 讲）**: 项目生命周期后段——单客户成果沉淀成产品（内环外环 + 平台提交 + 抽象层 + 交接）、私有知识护城河（四步转化：抽取/脱敏/结构化/入库）、定价（RaaS + OLA + 三种收费组合 + 客单价匹配表）、服务陷阱（a16z 四条件 + 用毛利换护城河 + 三条纪律）。
5. **复盘与行业落地（第 17–21 讲）**: 成功复盘（五步框架 + 坦帕医院案例）、翻车复盘（六大失败模式 + 四信号仪表盘 + 中国六道坎 + 止损）、行业落地三讲（金融/政企/医疗=治理即产品；制造/能源=从提效到降本；零售/客服=直接驱动业务）。
6. **成长篇（第 22–23 讲）**: 能力与面试（一纵一横一软 + 本体建模 + 四轮面试 + 转型路线 + 薪酬 + 30-60-90）、职业发展与陷阱（晋升双通道 + 五个出口 + 什么时候别做 FDE）。

**论点之间的关系**: 递进 + 层层深入。第 1 章是「是什么/为什么」（认知），第 2–4 章严格按一个真实 FDE 项目的生命周期推进（进场→施工→沉淀变现，是主线且分量最重），第 5 章把方法放到真实行业战场验证（复盘+落地），第 6 章回到个人（成长）。一条暗线贯穿始终：**AI 负责「做出来」，人负责「判断是否做得好」**。

### 作者要解决的核心问题

中文世界关于 FDE 几乎只有概念讨论、没有系统实战内容，连「FDE 和外包有没有区别」都能吵成一团。作者要补上这块空白：FDE 到底怎么做——从进场、验证、施工、上线、沉淀、变现到职业发展，给出一套能直接上手的方法（清单、模板、话术、判断标准），并回答「真假 FDE 怎么分辨」。

## 2. 解释 (Interpretive)

### 关键术语 (作者本人的用法)

| 术语 | 作者的定义 | 和常识用法的差异 |
|---|---|---|
| FDE | Forward Deployed Engineer，前向部署工程师；一个「嵌入客户现场、主动交付有价值结果的产品探索者」 | 不是驻场开发/外包换名；内核是「探索」不是「交付」；分两层：岗位义（前线 Delta）+ 打法义（Delta+Dev 整套协作） |
| Delta | Palantir 前线部署工程师（FDE 的狭义本体），「一个客户、多种能力」 | 与后方 Dev 对立：Dev 是「一种能力、服务多个客户」 |
| Dev | Palantir 后方产品沉淀角色（PD 团队），把前线认知沉淀成通用平台能力 | 严格讲不是狭义 FDE，是平台型角色 |
| Echo | Palantir 前线「部署策略师」，偏业务/产品，与 Delta 搭档 | 注意：Sho Shimoda 的书里用 Echo 指后方沉淀角色，与 Palantir 口径相反 |
| 真问题 vs 嘴上的需求 | 客户「嘴上说的需求」往往是他自己想的解决方案；真问题要穿过两层陷阱（客户把方案当问题、你把客户的合理选择当 bug） | 与「需求收集」的区别：真问题必须可衡量、亲历、可验证、可归因 |
| 北极星指标 | 直接反映业务成功的核心指标（如 GMV），须同时满足三条件：与商业价值强相关、努力可影响、可拆解可归因 | 不是 UV/PV 等过程指标 |
| 翻译问题 | 把「客户想要什么」翻译成「业务上发生什么变化、用哪个数字衡量」（Daniel Vaughan 语） | 与「需求分析」区别：产出是「可测量、可验收的结果陈述」 |
| MVP / MVA | 最小可行产品（对外验证价值）/ 最小可行架构（对内验证技术可行性） | MVA 常被忽略；MVA 是「能毕业进生产架构的种子」 |
| 负债区 / 隔离区 / 资产区 | 客户项目代码落地的三个位置：写死在部署实例深处（负债）、feature flag+配置层（隔离）、抽象进平台（资产） | 核心纪律：代码写在哪决定它是资产还是负债 |
| 内环 / 外环 | 内环=在客户现场把东西做出来；外环=把单客户成果固化成产品/公司能力 | 外环是「碎石路铺成高速公路」，只有内环就是一次性交付 |
| 平台提交 | 把现场发现的可产品化问题，结构化地正式交给平台团队进入产品路线图（含现象/根因/建议/受益面四要素） | 不是「转发客户原话」 |
| 前后方握手 | FDE 团队与平台工程团队的固定周会，共同对需求 pipeline 负责 | 飞轮在此转起来或卡住 |
| 私有知识 / know-how | 从多个客户现场提炼的行业规律（天生脱敏、可跨客户共享），区别于客户数据 | 相对同行「私有」，不是相对客户「私有」 |
| OLA | 结果级协议（Outcome-Level Agreement），写清「产出什么结果/怎么衡量/谁负责/审核节奏」四要素 | 替代传统按功能验收的合同 |
| RaaS | Result as a Service，按结果付费；以「基础费 + 效果分成」落地 | 区别于按人天/按席位/按功能买断 |
| 治理即产品 | 强监管行业里，把安全/合规/审计/控制权做成可报价、可交付、可复用的产品能力 | 治理不是成本，是入场券和核心竞争力 |
| 本体论 (Ontology) | 把行业的实体、关系、事件抽象成通用语义层（如零售的会员/商品/订单/门店） | 类似领域模型，但范围是「整个行业共用的一份」 |
| Harness | AI 模型之外的一切控制机制（执行环境/工具/护栏/上下文组装/输出验证）；Agent = Model + Harness | 强调：模型不是自研的，Harness 才是自己的工作量 |
| 评估集 | 把「好」落成可跑的输入-期望用例；分黄金集/异常场景集/安全对抗集三类 | 从「上线前验收工序」变成「开发迭代的方向盘」 |
| 棘轮原则 | 评估分数每上一个台阶就成为新地板，不允许任何改动打回地板以下 | 防「考不过就改考卷」 |
| 评估面 / 客户面 | 系统质量标准由 FDE 定（评估面）；业务口径/验收由客户定（客户面） | 同一把尺子，双方各管一段 |
| 接单员陷阱 | 讨好客户、来一个需求接一个，从专家降级成「一双好用的手」 | 客户信任恰恰来自你敢说「不」 |
| 永久拐杖 | 客户永远离不开你，你也抽不出身，双输 | 反模式，不是护城河 |
| 信任谱系 | 信任不是开关，是一段有深浅的谱系，靠一次次兑现承诺往上走 | — |
| 奇怪的星期二 | 没人写进文档、每隔一阵来一次、操作员见怪不怪却不正式提起的怪情况 | 挖阻塞点的问法：别问「一般怎么做」，问「上周二下午三点在忙什么」 |
| 自治阶梯 | 交接三步：FDE 主导→客户运营+FDE 后方→客户独立 | FDE 真正的交付物包括「有能力的客户团队」 |
| 六大失败模式 | 咨询陷阱、每客户雪花化、英雄工程师、demo 债务螺旋、赞助人崩塌、倦怠死亡螺旋 | 有稳定类型，可提前识别止损 |
| 中国六道坎 | 利润坎/人才坎/晋升坎/抽象坎/组织坎/市场坎 | 结构性原因，放大六大失败模式 |
| 一纵一横一软 | FDE 能力模型：技术深度(4 方向) + 能力广度(5 簇) + 软实力 | 纯技术只占「两个半」 |
| 30-60-90 框架 | 入职后前 30/60/90 天逐步扩大责任边界 | 不是熬资历，是逐步交出职责 |

### 核心命题 (用自己的话)

1. 写代码不再是稀缺能力，「把 AI 交付成业务结果 + 把现场认知沉淀回产品」才是稀缺能力；这是 AI 时代价值链上的结构性位置。
2. 判断真假 FDE 只看两条最硬的线：现场认知有没有回流到产品、第二个客户是不是做得更容易（其余薪资/代码/负责对象都是辅助验证）。
3. 中国 To B 的十年困境（六大特征：关系销售、定制、低价、拖欠尾款、私有部署、现场服务）根子是风险与责任的错配 + 乙方抽象能力不足 + 中国管理流程本身不标准；「标准软件撞上不标准流程」是更底层的病根。
4. 进场第一战最大的陷阱是把「嘴上需求」当「真问题」；要穿过两层陷阱（客户把方案当问题、你把客户的合理选择当 bug）。
5. 选场景是一次翻译：把「想要什么」翻译成「业务上什么变化、用哪个数字衡量」，北极星三条件是那把尺子；「敢写放弃」比「会做需求」更接近上限。
6. 技术负责把事做对，人负责把事做成；在真实客户组织里，技术价值必须先过「人」这一关（干系人、信任、汇报、政治）。
7. demo 是让客户说「不对」的工具，不是让客户说「哇塞」的道具；demo 赢的是「继续往下走的资格」，不是合同。
8. 在别人家的地基上施工，纪律比速度重要；代码写在哪（负债区/隔离区/资产区）决定它是资产还是负债。
9. 数据安全是生死线，护栏必须在第一天焊死；AI 是放大器，既放大效率也放大小疏忽。
10. AI 项目先定义「好」再写第一行 Prompt；评估集是开发迭代的方向盘，不是上线前的验收工序；「先定义好、按曲线验收」取代「一次签字验收」。
11. 个人好用和企业可用是两个问题；治理不是负担，在强监管行业「治理就是产品」。
12. FDE 打法有个核心循环：先在一个客户身上做深，再决定什么沉淀回平台（内环让客户满意，外环让公司值钱）。
13. AI 时代代码是包袱，需求理解、行业 know-how、客户信任才是资产；私有知识（天生脱敏、可跨客户共享）是真正的护城河。
14. 按工具卖，FDE 必然沦为成本中心；把业务结果写进合同（OLA + RaaS），FDE 才能从「成本」变「收入」。
15. 服务陷阱不是一次错误决策，而是「客户专属工作一点点跑赢通用平台工作」的渐进滑落；用毛利换护城河，关键在「换」——必须换回可复用产品能力、数据入口、工作系统。
16. 失败有稳定类型（六大失败模式），风险有可观察信号（四信号仪表盘）；要提前识别、及时止损。
17. AI 负责「做出来」（调研/demo/代码/放大交付），人负责「判断」（哪个是真问题、方向对不对、红线在哪、什么算验收、怎么定价、该不该拒绝）。

### 论证链

作者的论证主线是「定位→方法→商业→职业」四层递进，用**亲身经历（神策 11 年、Omni-Growth 三人团队）+ 公开标杆案例（Palantir/OpenAI/Anthropic）+ 可查数据（MIT NANDA 报告、IDC、智谱招股书）**三重证据支撑：

- **定位层**：用 Palantir 的 Delta/Dev 机制 + OpenAI/Anthropic 招聘动向证明「交付成为胜负手」这一判断不是个人选择而是行业共识；用 MIT「95% 零回报」+ IDC「88% PoC 未进生产」证明瓶颈在落地不在模型。
- **方法层**：用 Daniel Vaughan 的「五天发现法」「翻译问题」、Sho Shimoda 的「MVP/MVA」「六种失败模式」等同行框架，与作者自己驻场的真实细节（投手排期偏移、「奇怪的星期二」）互相印证，把方法落到可操作的清单。
- **商业层**：用 ServiceNow/Workday/Palantir 的毛利曲线 + Salesforce 的学费，论证「重服务可以换护城河但必须能毕业」；用智谱招股书（本地化部署占收入 84.5%）证明类 FDE 模式在国内财务上可行。
- **职业层**：用「八个资深工程师出一个 FDE」、Palantir 前员工成为 YC 创始人密度高，论证能力稀缺与职业溢价。

## 3. 批判 (Critical) ★

### 作者的时代局限

- **数据时点敏感**：全文大量引用 2025–2026 年的招聘/财务数据（OpenAI 150 名 FDE、智谱招股书、Palantir 毛利率 82.4%），这些数字快速过时，作为「证据」的时效性有限。
- **新岗位无成熟形态**：作者自己也承认「国内还没有公开的 FDE 岗位数量和薪资中位数」，即中国 FDE 尚处探索期，其结论是「窗口期」判断而非已验证事实。

### 作者的立场盲点

- **乙方视角**：作者是 To B 供应商（神策 CTO），整套方法论默认「甲方愿意深度配合、愿意改变自己」，对甲方内部执行难度、甲方 IT/业务的阻力着墨偏少，只在第 5 讲「客户四问」和第 23 讲「甲方视角」点到。
- **大客户/高客单价中心**：大量案例来自 Palantir/OpenAI/金融/政企等重模式、高客单价场景，对中小客户、低客单价市场的适用性需要自行换算（作者在匹配表中给出了「轻/中/重 FDE」分层，但论证重心仍偏向重模式）。
- **精英叙事**：作者自身是清华系 + 独角兽 CTO 背景，其「一个人打穿全链路」的能力门槛（八分之一）对普通从业者有距离感，课程对「够不到门槛的人」给出的路径相对薄弱。

### 未被证明的假设

- **「认知回流产品」必然可规模化**：整课把「外环」视为核心价值，但「哪些现场认知真的能抽象成跨客户通用能力」的判据仍偏经验化（「等第二个样本出现」），缺乏可复制的量化标准。
- **效果可归因**：定价篇反复依赖「北极星三条件 + 归因口径」，但真实业务中「归因」本身极难，作者默认归因可谈清，对「归因谈不清时怎么办」只给了「谈清」这一种解法。
- **AI 能力持续增强的线性外推**：全文默认 AI 会持续降低「做产品/改代码」门槛，若模型能力进入平台期，其「一个人打穿」的供给侧论证会被削弱。

### 最强反对意见

「FDE 不过是用 AI 武装的高级外包/驻场换皮」——这是作者自己反复正面回应的最强反驳（第 2 讲整讲）。反驳的力度在于：表面动作（驻场、写代码、出差、定制）与外包几乎无差别，且市面上一大半挂 FDE 名头的岗位确实就是售前或实施换皮。作者的反击逻辑（「看沉淀、看复利、看对什么结果负责」）在方法论上自洽，但**前提是公司真有「外环」和「毕业机制」**；若公司只有内环（这恰是多数现实），则 FDE 与外包的差别就只剩名义。换言之，作者的整套 FDE 叙事建立在「组织具备沉淀能力」这个隐含前提上，而这个前提本身稀缺且难验证。

> **以上批判会直接成为下游 skill 的 Boundary (B) 字段来源**
