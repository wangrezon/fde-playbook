# GLOSSARY — 《FDE 业务落地实战课》

> 全书共享术语词典。所有能力卡统一按本书的「作者用法」理解这些词，不使用字典义。
> 完整候选与出处见 candidates/glossary.md。

| 术语 | 作者的用法 | 和常识的差异 | 主要使用 skill |
|---|---|---|---|
| FDE | 嵌入客户现场、主动交付有价值结果的产品探索者；分岗位义（前线 Delta）与打法义（Delta+Dev 协作）两层 | ≠ 驻场开发/外包换名——内核是「探索」不是「交付」，真假只看「认知有没有回流产品」 | genuine-check |
| Delta | Palantir 前线部署工程师（FDE 狭义本体），「一个客户、多种能力」 | ≠ 普通驻场开发；与后方 Dev 对立 | genuine-check, sediment-pipeline |
| Dev | Palantir 后方平台角色，把前线认知沉淀成通用平台能力 | ≠ 狭义 FDE；「一种能力、服务多个客户」 | sediment-pipeline |
| Echo | Palantir 前线「部署策略师」（偏业务/产品，与 Delta 搭档） | ⚠ 双口径：Shimoda 用它指后方沉淀角色，与 Palantir 相反，引用须声明口径 | sediment-pipeline |
| 基于 AI 的定开 | 用 AI 几天搭出定制系统，仍是给单个客户写定制代码 | ≠ FDE——AI 只改交付效率、不改交付性质，是「高效的高级外包」 | genuine-check |
| 中国六道坎 | 利润/人才/晋升/抽象/组织/市场六道结构性现实条件 | ≠ 六大失败模式——六道坎是「放大失败的环境条件」，不是失败类型本身 | failure-identification |
| 真问题 vs 嘴上的需求 | 穿过两层陷阱（客户把方案当问题、你把合理选择当 bug）后，满足五标准的问题 | ≠「需求收集」——真问题须可衡量、亲历、可验证、可归因 | five-day-discovery |
| 奇怪的星期二 | 没人写进文档、每隔一阵来一次、操作员见怪不怪却不正式提起的怪情况 | ≠ 一般流程调研——问「一般怎么做」只能得到被整理过的标准流程 | five-day-discovery |
| 翻译问题 | 把「客户想要什么」翻译成「业务上什么变化、用哪个数字衡量」 | ≠ 需求分析——产出是「可测量、可验收的结果陈述」 | translation-northstar |
| 北极星指标 | 同时满足三条件（强相关/可影响/可拆解可归因）的核心指标 | ≠ UV/PV 等过程指标；是 GMV 而非「最重要的一个指标」 | translation-northstar |
| 接单员陷阱 | 讨好客户、来一个需求接一个，从专家降级成「一双好用的手」 | ≠ 客户满意度高——客户信任恰恰来自你敢说不 | stakeholder-map, use-case-prioritization |
| 永久拐杖 | 客户永远离不开你、你也抽不出身，双输 | ≠ 护城河——真正的护城河是「客户能独立、公司沉淀下知识」 | autonomy-ladder |
| 信任谱系 | 信任不是开关，是一段有深浅、靠一次次兑现往上走的谱系 | ≠ 二元的「信任/不信任」 | stakeholder-map |
| MVP | 最小可行产品，面向客户证明「值不值得做」 | ≠ MVA——只证明价值，不证明技术站得住 | demo-driven |
| MVA | 最小可行架构，面向工程团队验证核心技术风险可控 | ≠ 一次性脚手架——是能毕业进生产架构的种子 | demo-driven |
| 负债区/隔离区/资产区 | 代码落地三位置：客户副本深处（负债）/feature flag+配置层（隔离）/平台层（资产） | 核心纪律「写在哪决定是资产还是负债」；纪律有两句 | code-placement |
| 四层知识库 | 产品使用/跨行业共性/行业特有/企业特有四层 | ≠ 堆进一个库——上三层可共享，企业特有层「一个字不能带出门」 | knowledge-layering |
| Harness | AI 模型之外的一切控制机制，Agent = Model + Harness | ≠ 模型本身——模型不是自研的，Harness 才是自己的工作量 | eval-driven |
| 评估集 | 把「好」落成可跑的输入-期望用例，分黄金/异常/安全对抗三类 | ≠ 上线前验收工序——是「开发迭代的方向盘」，先于第一行 prompt 建 | eval-driven |
| 棘轮原则 | 评估分数每上一个台阶成为新地板，任何改动不许打回地板以下 | ≠「这次先上了再说」——防「考不过就改考卷」 | eval-driven |
| 评估面/客户面 | 系统质量标准归 FDE（评估面），业务口径/验收归客户（客户面） | 同一把尺子双方各管一段，不把评估外包也不越界替客户定口径 | eval-driven |
| HITL 人工检查点 | 按风险分层：自动执行/执行后通知/执行前确认三级 | ≠ 事事人批也≠全部放行；放权由数据（采纳率+兑现率）决定 | go-live |
| 全链路留痕 | 从输入、上下文、prompt 到推理、工具调用、输出全程留痕，四类：决策依据/数据来源/操作记录/反向回滚 | ≠ 只记结果日志——连推理过程一起记，留存期匹配监管窗口 | go-live |
| 治理即产品 | 把模型/数据/代码/决策权的控制要求做成可报价、可交付、可验收、可复用的产品能力 | ≠「治理是成本」——在强监管行业是入场券和核心竞争力 | regulated-industry |
| 内环/外环 | 内环在客户现场交付价值，外环把单客户成果固化成产品能力 | 只有内环没外环，复利为零，是「套着软件外壳的咨询公司」 | sediment-pipeline |
| 平台提交 | 把可产品化问题结构化交给平台团队，四要素：现象/根因/建议/受益面 | ≠「转发客户原话」——是转交学习成果 | sediment-pipeline |
| 前后方握手 | FDE 团队与平台工程团队的固定周会，共同对需求 pipeline 负责 | ≠ 随意跨团队沟通——飞轮在此转起或卡住 | sediment-pipeline |
| 本体论（Ontology） | 把行业实体/关系/事件抽象成「整个行业共用的一份」语义层 | ≠ 单系统领域模型——抽象单位是业务语义，范围是行业级 | sediment-pipeline |
| 自治阶梯 | 交接三步：FDE 主导 → 客户运营+FDE 后方 → 客户独立 | ≠ 结项甩系统——交付物包括「有能力的客户团队」 | autonomy-ladder |
| 私有知识 | 服务客户过程中攒下的行业 know-how，天生脱敏、可跨客户共享 | 「私有」相对同行、不是相对客户；≠ 客户数据 | private-knowledge |
| OLA | 结果级协议，写清四要素：结果/衡量/负责人/审核节奏 | ≠ 按功能验收的传统合同——用客户业务语言写结果 | pricing-ola-raas |
| RaaS（效果付费） | Result as a Service，按结果付费，以「基础费 + 效果分成」落地 | ≠ 按人天/按席位/按功能买断 | pricing-ola-raas |
| 六大失败模式 | 咨询陷阱/雪花化/英雄工程师/demo 债务/赞助人崩塌/倦怠螺旋 | ≠ 一次性错误决策——是「看似合理决策逐步滑入」的稳定类型 | failure-identification |
| 一纵一横一软 | FDE 能力模型：技术深度(4方向)+能力广度(5簇)+软实力 | ≠ 纯技术岗——纯技术只占「两个半」 | capability-interview |
| 30-60-90 | 入职前 30/60/90 天逐步扩大责任边界 | ≠ 熬资历——是逐步交出职责，跳步会制造「已准备好」错觉 | capability-interview |
