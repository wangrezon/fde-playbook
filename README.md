## 能解决什么问题

- 判断一个岗位或团队是不是真 FDE，还是外包、售前、实施换了名字
- 进场前决定该不该接，五天内摸清真问题，而不是把嘴上需求当需求
- 把「想要什么」翻译成「什么变化 + 哪个数字」，并给场景排序、写出放弃
- 画干系人地图、组织汇报、用每周 demo 把模糊反馈收成工单
- 决定代码写在负债区、隔离区还是资产区，并守住集成、版本、知识和安全护栏
- 先定义「好」再写 prompt：评估集、上线检查、HITL、全链路留痕
- 把单客户成果沉淀回产品，写 OLA / RaaS，并识别服务陷阱与止损信号
- 按金融、制造、客服的行业约束落地，并做能力自评、面试和职业去留判断

不适用：具体代码实现与技术选型、具体投资标的，以及需要专业资质的医疗、法律、财务审计决策。

## 常驻原则

1. AI 负责「做出来」，人负责「判断是否做得好」。
2. 真假 FDE 只看两条硬线：现场认知是否回流产品，第二个客户是否做得更容易。
3. 进场最大的陷阱是把嘴上需求当成真问题。
4. demo 是让客户说「不对」的工具；MVP 验价值，MVA 验可行性。
5. 代码写在哪，决定它是资产还是负债；数据安全护栏第一天焊死。
6. 先定义「好」，再写第一行 prompt。
7. 内环让客户满意，外环让公司值钱。只有内环，就是套着软件外壳的咨询公司。

## 边界

- 路由表和能力索引都对不上的问题，应明确说超出本课范围，不要硬套框架。
- 医疗、法律、人身安全类决策停止套用本方法，转专业意见。
- 课程里的招聘数字、毛利率、招股书数据有时效，引用时标明出处和时点，不要当成长期事实。
- 方法论默认组织有「外环」和毕业机制。只有内环时，FDE 与外包的差别会塌成名义差别，判断时应先核对这个前提。
- 用 cangjie-skill 增量更新前，先比对 `BUILD_MANIFEST.json` 的 `published_hashes`。检测到本地手改时不得静默覆盖。
